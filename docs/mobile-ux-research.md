# Mobile web UX: comparison sources

Research for the mobile audit, 6 November 2026. These are comparison points, not a claim that the cited products are objectively the best-looking apps or that Slingshot conforms to a standard. The app references below are public first-party pages; the web crawler did not provide a comparable interactive mobile viewport, so their observations concern documented journeys and visible page content, not a visual assessment of current mobile layouts. The practical design implications are our judgments.

## Game and app comparisons

- [Lichess's home page](https://lichess.org/) exposes three plain choices: create a lobby game, challenge a friend, or play a computer; its quick-pairing view also lists ready-made match options. The useful comparison is task language and a short path to play. It is not evidence that Slingshot needs to copy its visual style or matchmaking system.
- [Chess.com's own start-game guide](https://support.chess.com/en/articles/8609779-how-do-i-start-a-game-on-chess-com) describes starting a game from the home screen with defaults, with customization available as a subsequent choice. Its [friend challenge guide](https://support.chess.com/en/articles/8588467-how-do-i-play-a-friend) explains that the mobile path starts at Play, then selects a friend and settings. These are documented product flows; the guide's mobile screenshots describe the native app, not proof of identical mobile-web presentation. Useful comparison: keep the common action and invite intent legible before showing advanced setup.

## Evaluation criteria

- **Comfortable targets:** [Apple's game-control guidance](https://developer.apple.com/design/human-interface-guidelines/game-controls) recommends 44 × 44 points for frequent controls, 28 × 28 points for less important game controls, thumb reach, visible press feedback and avoiding system areas. Points and CSS pixels are different units; treat 44 CSS pixels as a practical browser check, not an exact conversion or universal compliance rule. [WCAG 2.2 target size](https://www.w3.org/TR/WCAG22/#target-size-minimum) has a 24 × 24 CSS pixel AA minimum with exceptions; [WCAG's enhanced target criterion](https://www.w3.org/WAI/WCAG21/Understanding/target-size) uses 44 × 44 CSS pixels at AAA. Inspect hit regions, not icon dimensions alone.
- **Readable, adaptable layout:** [WCAG reflow guidance](https://www.w3.org/WAI/WCAG21/Understanding/reflow) asks that vertical content remain usable at 320 CSS pixels without two-dimensional scrolling, with exceptions for content requiring two dimensions. A game field may warrant such an exception; surrounding forms and controls should be examined independently. Test text enlargement as well as width. Apple's [layout guidance](https://developer.apple.com/design/human-interface-guidelines/layout) also calls for respecting safe areas and adapting to available space.
- **Contrast and hierarchy:** [WCAG 2.2](https://www.w3.org/TR/WCAG22/#contrast-minimum) specifies at least 4.5:1 for ordinary text and 3:1 for qualifying large text at AA, subject to exceptions; its [non-text contrast criterion](https://www.w3.org/TR/WCAG22/#non-text-contrast) specifies 3:1 for necessary visual information in controls and states. Measure the actual rendered foreground and background, including opacity and imagery. Decorative type and atmospheric effects should not make functional labels harder to scan; that is design judgment, not a numeric rule.
- **Alternatives to gestures:** [WCAG 2.2 dragging movements](https://www.w3.org/TR/WCAG22/#dragging-movements) requires a single-pointer alternative to author-defined dragging unless an exception applies. For tabs, [WAI's tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) describes a coherent relationship among tab, panel, selected state and keyboard interaction. Apply this when the control is truly a tabs widget, rather than adding ARIA roles mechanically to every row of buttons.
- **Keyboard and pinned actions:** [Chrome's web form guidance](https://developer.chrome.com/docs/modern-web-guidance/guides/forms/forms) recommends that the virtual keyboard not obscure input fields or actions. An on-screen keyboard changes the visual viewport; [MDN explains](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/CSSOM_view/Viewport_concepts) why layout and visual viewports can differ. Verify real Safari and Chrome devices, including browser chrome and landscape; emulated screenshots cannot prove keyboard behavior.
- **Motion:** [web.dev's reduced-motion guidance](https://web.dev/articles/prefers-reduced-motion) explains honoring the platform preference. Judge transitions for whether they help navigation, and check the game's own reduced-motion option as well as the OS setting.

## Review boundaries

These sources provide standards, platform advice, and examples of product decisions; they do not establish aesthetic quality scientifically. An audit needs direct screenshots and interaction checks at relevant phone sizes, in both languages and across the actual state transitions. Native-app recommendations are informative comparisons, not browser-specific mandates. Reserve explicit WCAG pass/fail conclusions for a complete criterion-specific test, including exceptions and assistive technologies.

## Direct mobile-web comparison, 6 November 2026

The audit also opened these public pages at 390 × 844 CSS pixels in Chrome mobile emulation. These are useful reference products, not an objective ranking of visual quality; both are chess products with different feature and commercial requirements.

- [Lichess](https://lichess.org/) places quick game choices in a simple grid and follows them with full-width, explicitly named actions for creating a game, challenging a friend and playing the computer. The result makes the main choice and the next action legible without understanding iconography. Its crowded secondary feed is not a pattern Slingshot needs to copy.
- [Chess.com’s online play page](https://www.chess.com/play/online), after dismissing the consent prompt, presents a clear new-game area with a prominent Start Game button and separately named Custom Challenge and Play a Friend actions. The sampled viewport was positioned partway down the chessboard, so this observation is about the visible play controls, not a full-page or game-flow audit.

The comparison is visual and editorial judgment informed by those screens, not usability-test evidence. Neither reference was signed in or tested end to end, and neither substitutes for comparing Slingshot on physical phones.
